# 에이전트 팀

> **에이전트 팀**은 Claude Code 세션 **여러 개가 한 팀**이 되어 일하는 기능입니다. 한 세션이 **팀 리더**로 일을 나누고, 팀원들은 **각자 독립된 컨텍스트**로 일하면서 **서로 직접 메시지**를 주고받습니다.

> **실험 기능이며 기본으로 꺼져 있습니다.** 세션 재개, 작업 조정, 종료 동작에 알려진 제약이 있습니다. 토큰도 **크게** 더 씁니다. 먼저 [서브에이전트](#/level3/subagents-advanced)로 충분한지 확인하세요.

## 서브에이전트와 무엇이 다른가
| | 서브에이전트 | 에이전트 팀 |
|---|---|---|
| 컨텍스트 | 각자 독립, 결과만 호출자에게 돌아옴 | 각자 **완전히 독립** |
| 소통 | 결과를 호출자에게 **보고** | 팀원끼리 **직접 메시지** |
| 조정 | 메인 에이전트가 **전부 관리** | 메시지로 **스스로 조정** + 공유 작업 목록 |
| 알맞은 일 | 결과만 필요한 **집중된 작업** | **토론과 협업**이 필요한 복잡한 일 |
| 토큰 비용 | 낮음 (요약만 돌아옴) | **높음** (팀원마다 별도 Claude) |

> **서브에이전트** = 빠르게 일하고 보고하는 보조. **에이전트 팀** = 서로 발견을 공유하고 반박하며 협업하는 동료.

## 언제 쓰나
팀은 **병렬로 탐색하는 가치**가 클 때 효과적입니다.
- **조사·검토** — 팀원이 문제의 서로 다른 면을 동시에 살피고 서로의 결론에 이의를 제기
- **새 모듈·기능** — 팀원마다 **서로 다른 부분**을 맡아 간섭 없이 개발
- **경쟁 가설로 디버깅** — 여러 가설을 병렬로 검증해 빨리 수렴
- **계층을 가로지르는 작업** — 프런트엔드·백엔드·테스트를 각각 한 팀원이 담당

**쓰지 말아야 할 때:** 순서가 중요한 작업, **같은 파일**을 고치는 작업, 의존성이 많은 작업은 한 세션이나 서브에이전트가 낫습니다. 조정 부담과 토큰 비용이 이점을 넘어서기 때문입니다.

## 켜기
환경 변수 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`를 `1`로 설정합니다. 설정 파일(`%USERPROFILE%\.claude\settings.json`)에 쓰면 매번 지정하지 않아도 됩니다.
```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```
- **대화형 세션에서만** 팀원을 만들 수 있습니다. 헤드리스(`-p`)와 Agent SDK에서는 이름을 붙인 서브에이전트도 **일반 서브에이전트**로 실행됩니다
- 켜 두면 Claude가 **스스로 이름을 붙인 서브에이전트가 팀원으로 실행**되어, 요청하지 않아도 팀이 만들어질 수 있습니다. 원치 않으면 값을 `0`으로 바꿉니다 (저장하면 열린 세션에도 바로 반영)

## 첫 팀 만들기
팀을 켠 뒤에는 **하고 싶은 일과 필요한 팀원을 말로 설명**하면 됩니다.

```text
TODO 주석을 코드베이스 전체에서 추적해 주는 CLI 도구를 설계하고 있어.
세 명의 팀원을 만들어서 서로 다른 관점으로 살펴봐 줘:
한 명은 사용자 경험, 한 명은 기술 구조, 한 명은 반대 의견을 맡는 역할(devil's advocate)로.
```
이 예가 좋은 이유는 **세 역할이 서로 기다리지 않고 독립적으로 탐색**할 수 있기 때문입니다. 그러면 Claude가:
1. **공유 작업 목록**을 만들고
2. 관점마다 **팀원을 생성**하고
3. 탐색을 진행시킨 뒤
4. 끝나면 **결과를 종합**합니다.

> Claude가 팀 대신 **서브에이전트**를 쓰기도 합니다. 서브에이전트도 같은 패널에 표시되므로 패널만으로는 팀이 만들어졌는지 알 수 없습니다. 서브에이전트가 만들어졌다면 **"에이전트 팀으로 만들어 줘"** 라고 분명히 다시 요청하세요.

## 화면과 조작
리더 터미널의 **에이전트 패널**(프롬프트 입력창 아래)에 팀원이 나열됩니다.

| 키 | 동작 |
|---|---|
| `↑` / `↓` | 팀원 선택 |
| `Enter` | 선택한 팀원의 **기록을 열고 직접 메시지** |
| `Esc` | 선택 해제. 팀원 기록을 보는 중이면 **그 팀원의 현재 턴을 중단** |
| `x` | 선택한 팀원을 중지 |
| `Ctrl+T` | 작업 목록 켜기·끄기 |

- 유휴(idle) 팀원은 모두 쉬면 30초 뒤 행이 **숨겨질 뿐 중지된 것이 아닙니다.** 이름으로 메시지를 보내면 다시 나타납니다
- 유휴 팀원이 3명을 넘으면 `2 idle agents`처럼 한 줄로 합쳐지고 `Enter`로 펼칩니다

### 표시 방식 두 가지
| 방식 | 설명 | 조건 |
|---|---|---|
| **in-process** (기본) | 모든 팀원이 **내 터미널 하나** 안에서 실행 | **어느 터미널이든 가능** |
| **분할 창(split panes)** | 팀원마다 **자기 창**. 모두의 출력을 한눈에 봄 | **tmux 또는 iTerm2 필요** |

> **Windows에서는** 기본인 in-process 방식을 쓰면 됩니다. tmux는 macOS에서 가장 잘 동작하며, 분할 창은 일반 Windows 터미널에서는 쓸 수 없습니다. 분할 창을 쓰려면 `"teammateMode": "auto"`를 설정하고 tmux나 iTerm2 안에서 실행해야 합니다 (WSL의 tmux 등).

## 팀 다루기
리더에게 **자연어로** 지시하면 조정·할당·위임은 리더가 합니다.

### 팀원 수와 모델 지정
```text
팀원 4명을 만들어서 이 모듈들을 병렬로 리팩터링해 줘. 각 팀원은 Sonnet을 써 줘.
```
팀원의 모델은 **위에서부터 먼저 맞는 것**으로 정해집니다.
1. 내 요청에서 **그 팀원에게 지정**한 모델
2. 서브에이전트 정의를 쓰는 경우 그 정의의 `model` (`inherit`면 리더의 모델)
3. 환경 변수 `CLAUDE_CODE_SUBAGENT_MODEL` (`inherit`가 아닐 때)
4. **리더의 현재 모델**

팀원의 모델은 **만들어질 때 고정**됩니다.

### 구현 전에 계획 세우게 하기
복잡하거나 위험한 작업은 **리더를 먼저 플랜 모드**로 바꾼 뒤 팀원을 요청하세요. 그러면 팀원도 계획이 나올 때까지 플랜 모드로 일합니다.
```text
인증 모듈을 리팩터링할 아키텍트 팀원을 만들어 줘.
```
계획이 끝나면 리더에게 **계획 승인 요청**이 가고, 승인되면 팀원이 구현을 시작합니다. (팀원의 권한 모드를 바꾸지 않았다면 요청이 도착하는 즉시 자동 승인됩니다. 리더가 직접 검토하게 하려면 실행 중인 팀원 화면에서 `Shift+Tab`으로 플랜 모드로 바꾸세요.)

### 팀원과 직접 대화하기
팀원은 **독립된 Claude Code 세션**이라 직접 추가 지시를 하거나 질문하고 방향을 바꿀 수 있습니다. 패널에서 팀원을 열면 일반 글과 스킬은 **그 팀원에게**, 내장 명령은 **리더 세션**으로 갑니다. (`/compact`, `/clear`, `/rewind`는 리더에 적용되므로 확인을 묻고, `/model`·`/fast`는 리더 설정이라 이 화면에서는 실행되지 않습니다.)

### 작업 할당과 가져가기
**공유 작업 목록**이 팀의 일을 조정합니다. 작업 상태는 **대기(pending) → 진행 중(in progress) → 완료(completed)** 이고, 다른 작업에 의존하면 **막힘(blocked)** 으로 표시되며 선행 작업이 끝나야 풀립니다.
- **리더가 할당**: "이 작업은 이 팀원에게"라고 지시
- **스스로 가져가기**: 팀원이 작업을 끝내고 **다음 미할당·막히지 않은 작업**을 알아서 집음 (파일 잠금으로 동시에 같은 작업을 집는 충돌을 방지)

### 팀원 종료
이름으로 요청합니다.
```text
researcher 팀원에게 종료하라고 해 줘
```
리더가 종료 요청을 보내고 팀원은 **승인하거나 이유를 달아 거절**할 수 있습니다. 팀 폴더는 세션이 끝나면 자동 정리됩니다.

### 훅으로 품질 관문 만들기
[훅](#/level3/hooks)으로 팀의 작업 품질을 강제할 수 있습니다. 종료 코드 `2`로 **피드백을 주며 막습니다.**
| 이벤트 | 시점 | 종료 코드 2의 효과 |
|---|---|---|
| `TeammateIdle` | 팀원이 쉬려고 할 때 | 피드백을 주고 **계속 일하게** 함 |
| `TaskCreated` | 작업이 만들어질 때 | 생성을 **막음** |
| `TaskCompleted` | 작업이 완료 처리될 때 | 완료를 **막음** |

## 구조
| 구성 요소 | 역할 |
|---|---|
| **팀 리더** | 팀원을 만들고 일을 조정하는 **메인 세션** |
| **팀원** | 각자 맡은 작업을 하는 **별도의 Claude Code 인스턴스** |
| **작업 목록** | 팀원이 가져가서 완료하는 **공유 작업 목록** |
| **메일함** | 에이전트 사이의 **메시지 시스템** |

- 팀 설정은 `%USERPROFILE%\.claude\teams\{팀이름}\config.json`(세션이 끝나면 삭제), 작업 목록은 `%USERPROFILE%\.claude\tasks\{팀이름}\`(세션이 끝나도 남음)에 저장됩니다. 팀 이름은 `session-` + 세션 ID 앞 8자입니다
- **팀 설정 파일을 손으로 고치지 마세요.** 다음 상태 갱신 때 덮어써집니다. 프로젝트 안의 `.claude/teams/teams.json` 같은 파일은 **설정으로 인식되지 않습니다**
- 의존성이 풀리는 것은 **자동**입니다. 선행 작업이 끝나면 의존하던 작업의 막힘이 풀립니다

### 서브에이전트 정의를 팀원 역할로 재사용
`security-reviewer`처럼 한 번 정의한 서브에이전트를 **팀원으로도** 쓸 수 있습니다.
```text
security-reviewer 에이전트 유형으로 팀원을 만들어 인증 모듈을 점검해 줘.
```
| 정의의 항목 | 팀원에게 적용 |
|---|---|
| `tools` | 적용 (in-process 팀원에게는 메시지·작업 도구가 추가됨) |
| `model` | 적용 (내가 모델을 지정하지 않았을 때) |
| 본문(프롬프트) | in-process는 기본 프롬프트에 **추가**, 분할 창은 **대체** |
| `skills` | **적용 안 됨** (프로젝트·사용자 설정의 스킬을 로드) |
| `mcpServers` | 분할 창 팀원에게만 적용 |

### 권한
- 팀원은 **리더의 권한 모드로 시작**합니다. 생성할 때 팀원별로 다르게 정할 수 없습니다. 리더가 `bypassPermissions`(`--dangerously-skip-permissions`)면 **팀원도 같습니다**
- 팀원의 허가 질문은 **리더 세션에 표시**됩니다. 거기서 승인하세요
- 다른 에이전트가 보낸 메시지는 "다른 Claude 세션에서 왔다"고 표시되며 **내 승인을 대신할 수 없습니다.** 거절당한 일을 다른 팀원을 통해 우회할 수도 없습니다

### 컨텍스트와 소통
- 팀원은 시작할 때 `CLAUDE.md`, MCP 서버, 스킬을 로드하지만 **리더의 대화 기록은 물려받지 않습니다.** 리더가 넘긴 **시작 프롬프트**만 받습니다
- 메시지는 자동 전달되고, 팀원이 끝나면 **리더에게 유휴 알림**(최종 답 포함)이 갑니다
- 팀원 이름은 리더가 붙입니다. 이후 요청에서 부를 수 있게 **만들 때 이름을 지정**하세요

## 활용 예시

**병렬 코드 리뷰** — 리뷰어 한 명은 한 번에 한 가지 유형의 문제에 쏠리기 쉽습니다. 기준을 나눠 각자 맡깁니다.
```text
PR #142를 검토할 팀원 세 명을 만들어 줘.
- 한 명은 보안에 미치는 영향
- 한 명은 성능에 미치는 영향
- 한 명은 테스트 범위 검증
각자 검토하고 결과를 보고하게 해 줘.
```

**경쟁 가설 디버깅** — 한 에이전트는 그럴듯한 설명 하나를 찾으면 멈추는 경향(앵커링)이 있습니다. 서로 **반박**하게 하면 살아남은 가설이 진짜 원인일 가능성이 높습니다.
```text
사용자들이 앱이 메시지 하나를 처리하고 종료된다고 해.
서로 다른 가설을 조사할 팀원 5명을 만들어 줘. 서로 대화하며 상대의 가설을 반박해서,
과학 토론처럼 진행해 줘. 합의된 결론을 조사 문서에 정리해 줘.
```

## 잘 쓰는 법
- **충분한 맥락을 넘기세요** — 대화 기록을 물려받지 않으므로 시작 프롬프트에 구체적인 정보(경로, 쓰는 기술, 원하는 보고 형식)를 담습니다
  ```text
  보안 리뷰어 팀원을 만들어 줘. 프롬프트: "src/auth/의 인증 모듈에서 보안 취약점을 점검해.
  토큰 처리, 세션 관리, 입력 검증에 집중해. 앱은 httpOnly 쿠키에 저장한 JWT를 써.
  발견한 문제는 심각도와 함께 보고해."
  ```
- **팀 크기** — 대부분 **3~5명**으로 시작하세요. 토큰은 인원에 **비례해** 늘고 조정 부담도 커집니다. 집중한 3명이 산만한 5명보다 낫습니다
- **작업 크기** — 너무 작으면 조정 비용이 더 크고, 너무 크면 확인 없이 오래 가서 헛수고 위험이 커집니다. **함수·테스트 파일·검토 한 건처럼 결과물이 분명한 단위**가 알맞습니다. 팀원당 5~6개 작업이면 활발히 돕니다
- **리더가 직접 구현하려 들 때** — "팀원들이 작업을 끝낼 때까지 기다려"라고 하세요
- **처음에는 코드를 쓰지 않는 일로** — PR 리뷰, 라이브러리 조사, 버그 원인 조사가 좋습니다
- **파일 충돌 피하기** — 두 팀원이 **같은 파일**을 고치면 덮어씁니다. 팀원마다 **다른 파일 묶음**을 맡기세요
- **지켜보기** — 진행을 확인하고 안 되는 방향은 바꾸세요. 오래 방치할수록 헛수고가 커집니다

## 문제 해결
| 증상 | 확인할 것 |
|---|---|
| 팀원이 안 보인다 | 패널에서 `↑↓`로 선택해 `Enter`. 유휴로 **숨겨졌을** 수 있음. 작업이 팀이 필요할 만큼 복잡한지. 분할 창을 요청했다면 tmux·iTerm2 설치 |
| 팀 대신 서브에이전트가 나온다 | "에이전트 팀으로 만들어 줘"라고 명시 |
| 서브에이전트를 불렀는데 팀원이 나온다 | `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`를 `0`으로 |
| **허가 질문이 너무 많다** | 팀원을 만들기 **전에** 자주 쓰는 작업을 권한 설정에서 미리 허용 ([권한 규칙 심화](#/level3/permissions-deep)) |
| 팀원이 **일찍 멈춘다** | 팀원 화면을 열어 출력 확인 → 추가 지시를 주거나 **대체 팀원**을 만들기 |
| 리더가 **다 끝나기 전에 끝냈다고 함** | "계속 진행해"라고 지시 |
| 작업이 **계속 막혀 있다** | 실제로는 끝났는데 완료 표시를 안 한 것일 수 있음. 직접 갱신하거나 리더에게 팀원을 재촉하게 하기 |

## 알려진 한계 (실험 기능)
- `/resume`, `/rewind`로 **in-process 팀원이 복원되지 않습니다.** 재개 후 리더가 사라진 팀원에게 메시지를 보내려 하면 새 팀원을 만들게 하세요
- 작업 상태 갱신이 **늦을** 수 있고, 종료도 **느릴** 수 있습니다 (현재 요청을 끝낸 뒤 종료)
- 세션당 **팀 하나**. 팀을 더 만들거나 세션 간 공유할 수 없습니다
- **중첩 팀 없음** — 팀원은 팀원을 만들 수 없습니다. 리더만 팀을 관리합니다
- 리더는 **고정**입니다. 팀원을 리더로 바꿀 수 없습니다
- in-process 팀원의 서브에이전트는 **포그라운드로만** 실행됩니다

## 팀이 필요 없다면
| 방법 | 설명 |
|---|---|
| [서브에이전트](#/level3/subagents-advanced) | 한 세션 안의 가벼운 보조. 서로 소통할 필요가 없는 일 |
| 세션 간 메시지(cross-session messaging) | 내가 따로 띄운 세션끼리 Claude가 발견을 전달 |
| [Git worktree](#/level2/git-branch-worktree) | 내가 직접 여러 세션을 병렬로 운영 (자동 조정 없음) |

## 확인 체크
- [ ] `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`을 설정했다
- [ ] 코드를 쓰지 않는 조사·검토 작업으로 팀원 3명을 만들어 봤다
- [ ] 패널에서 팀원을 열어 **직접 메시지**를 보내 봤다
- [ ] 팀을 쓰면 토큰을 더 많이 쓴다는 점을 이해했다 (처음에는 짧은 작업으로 시험)

## 자주 하는 실수
- **순차 작업**이나 **같은 파일** 수정에 팀을 씀 → 서브에이전트나 한 세션이 낫습니다
- 시작 프롬프트에 **맥락을 빠뜨림** → 팀원은 리더의 대화를 모릅니다
- 팀원을 **너무 많이** 만듦 → 토큰이 인원에 비례해 늘어납니다
- 팀을 방치 → 헛수고 위험이 커집니다
- 팀 설정 파일(`config.json`)을 직접 고침 → 덮어써집니다
